## 从源码构建


### 前置要求

| 组件 | 版本 | 说明 |
| --- | --- | --- |
| 编译器 | MSVC（本机实测 14.51） | 需要 C++20/23 的 `std::expected` 与 `std::format` |
| CMake | ≥ 3.28 | — |
| Ninja | — | 生成器 |
| Conan | 2 | 依赖：spdlog 1.17.0、GoogleTest 1.17.0，Release 档另领 Tesseract 5.5.2 |
| Qt | 6.11，含 Core / Gui / Widgets / Concurrent / Svg / Network | 用 msvc2022_64 套件 |

| ffmpeg | 官方静态构建（gyan.dev） | 打包时需要：`scripts/FetchFfmpeg.ps1` 按钉好的 URL + SHA-256 取进 `vendor/Ffmpeg/`；开发期 PATH 上有一份也行 |

机器相关的路径只出现在 `scripts/WindowsBuild.bat` 里，工程不写死绝对路径。

### Windows

```bat
set QTDIR=G:\Tools\Qt\6.11.1\msvc2022_64
scripts\WindowsBuild.bat release
build\release\bin\GyanisScribe.exe --selftest
```

`WindowsBuild.bat` 自己调 `vcvars64`、按预设配置、编译并跑 `ctest`，一条命令就是一条门禁。
预设两档：`debug` 与 `release`。Windows 上两档都带系统识别后端（`Windows.Media.Ocr`），
只有 `release` 额外领 Tesseract——上游 leptonica 的 Debug 包与其 `cpp_info` 对不上，
细节与撤除判据见 [docs/OcrBackends.md](OcrBackends.md)。

`CMakePresets.json` 里只有 `debug` 与 `release` 两档；工具链由进入构建的那一步决定：
`WindowsBuild.bat` 先调 `vcvars64`，Conan 再按主机 profile（`conan/Profiles/WindowsMsvc2022`）指过去。



## 打包


```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\WindowsPackage.ps1
```

产出绿色目录 + zip + NSIS 安装器，落在 `dist/`。脚本用 `windeployqt` 按可执行体的**实际导入**摆好
Qt 运行时，然后在 staging 目录里把 `PATH` 收窄到只剩 `System32`、并清掉 `QTDIR` 与
`QT_PLUGIN_PATH` 那几条提示，再跑一次 `--selftest` 与 `ffmpeg.exe -version`。
为什么收窄：开发机的 `PATH` 上本来就有 Qt，缺了哪件 DLL 也会被本机那份悄悄补上，
「本机能跑」就不是「包装完能跑」的证据。这条判据本身也验过能不能红：在同一份 staging 里
把 `Qt6Widgets.dll` 挪开，`--selftest` 的退出码变成 `-1073741515`（`0xc0000135` = 找不到 DLL），
放回又回到 0。安装器带卸载段。

VC++ 运行库也随包带：可执行体导入 `MSVCP140.dll` 与 `VCRUNTIME140.dll`（还有 `_1`、`_2` 两份），
这几件不属于 Windows 自带的系统映像，新装机上要么先装 redist 要么程序起不来。打包脚本按编译器版本
从工具链的 `VC\Redist\MSVC\<版本>\onecore\x64\Microsoft.VC145.CRT` 取那五份摆到可执行体旁边
（Windows 先搜程序目录，加载的就是随包这一份），缺任一件当场中止；UCRT（`api-ms-win-crt-*`）不搬，
那是 10/11 自带的。`windeployqt --compiler-runtime` 在这套 Qt 上一个 CRT 都不落地（实测），所以自己拷。

「装完即用」这一条也真机量过：把 `dist/` 里的安装器静默装进一个空目录（`/S /D=<空目录>`），
装出来的目录里 `GyanisScribe.exe`、`ffmpeg.exe`、`tessdata/` 两份语言包、`licenses/`、
`translations/GyanisScribe_en.qm`、`platforms/qwindows.dll` 与 `Uninstaller.exe` 全在；
就在那个目录里把 PATH 收窄到只剩 `System32` 跑 `--selftest`，退出码 0，
`ffmpeg.exe -version` 也起得来（9.0.2-essentials_build）；随后 `Uninstaller.exe /S` 退出码 0，
装出来的目录和 HKLM 里那条卸载登记键都不在了。

```bash
GYANISSCRIBE_AUDIO_DEVICE=@device_cm_{...}\wave_{...} # 取声端到端（要用 dshow 的 Alternative name，不是友好名）
```

另有三条不编译源码的静态门禁，作为 ctest 用例注册在 `tests/Style/`：

| 用例 | 钉住什么 |
| --- | --- |
| `Style.QtStringPlaceholders` | `QString` 占位符不许 `{}` 与 `%1` 混用——混用编译期无声，运行时把「选择{}的目录」原样摆给用户 |
| `Style.TranslationCatalog` | 源码里每一条走 `uiText` 的文案都必须在 `.ts` 里有非空译文（`uiText("…")` 的字面量、表行里的标签、按位置对齐的档位标签数组这三形都算），否则英文档下会安静地显示中文 |
| `Style.SourceConventions` | 五件事：路径不得按窄串交给第三方库；按枚举分派的开关要覆盖每个值（MSVC 与 GCC 的默认告警都不报这种漏项）；声明出来的信号要有人接；`src/` 顶层只许七模块目录；仓库根的顶层目录一律小写（见脚本头部五条判据） |

另有一条静态检查不进 ctest，单独跑：**clang-tidy**（`scripts/check-clang-tidy.py` + 仓库根 `.clang-tidy`）。
检查面与命名规范**直接复用 AsynGyanis 的那一份**（逐条列检查清单 + `readability-identifier-naming` 一组取值），
两边口径一样，不在这个仓里另裁一份。覆盖面就定在 `src/`：`build/**/_autogen` 与 `moc_` 是生成代码，
`tests/` 的命中大多来自 gtest 宏造成的假阳性，两边都不进来。要真解析每个 TU（Qt 头的开销在那儿），
跑一次十几分钟，所以不进 ctest；CI 是独立 job，本机改到 C++ 面时手动跑：

```
python scripts/check-clang-tidy.py        # 默认 build/debug；换档用 --build-dir build/release
```

判红口径与 AsynGyanis 相同：**只有「本仓代码没解析成」才拦**（退 1，这不等于「检查通过」）；
发现项逐条报出来但**不阻塞**——clang 把 MSVC 的 `/WX` 读成 `-Werror`，clang 独有的几类会以 error
的面目出现，那是发现项不是没跑成；clang 进不去的第三方头（解析失败落在依赖头里）单独放行并报出名字。
退 2 是工具自己坏了：找不到 clang-tidy / 没有编译数据库 / 找不到 vcvars / 处理记录少了。
clang-tidy 按 PATH 找，也可用 `GYANISSCRIBE_LLVM_DIR` 指到 bin 的上一层；每个 TU 都在 vcvars 之后的环境里跑
（`wrl/client.h` 在只有 vcvars 才会加上的 winrt 目录里），`VCVARS` 环境变量优先、其次按 vswhere 找。

### 持续集成

`.github/workflows/ci.yml` 把上面两条线搬上 GitHub Actions（windows-2022 runner）：
`debug` job 装 Qt / Conan / Ninja 后直接调 `scripts\WindowsBuild.bat debug`——与本机同一条入口，
失败时把 `LastTest.log` 作为 artifact 带出来；`clang-tidy` job 只 configure 出编译数据库再跑上面那条静态检查，
不 build，报告作为 artifact 上传。runner 上要显式给的三样（Qt 路径、vcvars64、Conan 档位里的 MSVC 版本行）
在 workflow 注释里逐条写明。
**状态**：2026-10-17 **首次全绿**（run `38951666346`：Debug 15m9s、clang-tidy 29m26s；946 条里 939 过、0 失败、
7 条环境门控跳过——runner 上没有随包的 ffmpeg 与真光标那一档）。首绿之前修了五轮，逐轮死点都记在提交里：
Qt 6.11 的仓库布局（aqt 钉版）、`qtimageformats` 缺件、本地 VS18 与 runner VS2022 的两处不兼容
（`constexpr std::cos` 与内联析构的不完整类型）、两条「跟着机器走」的用例判据。
clang-tidy 的报告每次运行都作 artifact（`clang-tidy-report`）上传。

用例结构逐级镜像 `src/`，统一 GoogleTest，不引入第二个测试框架。
共用同一份外部资源（真实缓存目录、临时文件）的用例用 CMake 的 `RESOURCE_LOCK` 串行化——
`ctest -j` 把每条用例当独立进程启动，进程内互斥救不了。

## 性能实测


需求 §十一 的指标与它们的实际测量方法——没测过的直接写「未测」，不拿推测充数：

| 指标 | 本机实测 | 方法 |
| --- | --- | --- |
| 截图延迟 < 100ms | 抓一帧中位 **7.3ms**（DXGI 桌面重复；同一次运行里 Qt 的 `grabWindow` 是 28.8ms）。整条框选链——铺遮罩 → 拖框 → 交付成品——中位 **8.5 / 10.4 / 10.9ms**（三次各 5 轮，min 7.3 / max 34.4；那个 34 是每轮里第一次的冷启动开销） | 两条都是专门的读数用例，都**不断言时间**：抓帧那条 `QScreenCaptureSourceFixture.ReportsMedianGrabCostOfBothPrimitives`（12 轮中位、每轮先搅动一下桌面保证拿到的是新帧），整链那条 `CaptureServiceFixture.ReportsTheCostOfOneWholeInteractiveCapture`（真的铺遮罩、真的拖一块再确认）。机器：2560×1440、dpr 1.0、单屏；**Release 档**——同一条抓帧用例在 Debug 档读到 Qt 39 / DXGI 14，两档不可混用 |
| OCR 单张 < 1s | **4K（3840×2160）识别一次中位 428 / 431ms**（两次各 5 轮，min 424 / max 446）——需求给的是 <1s，4K 上留约 2.3 倍余量；小图那两个旧读数留着看趋势：640×160 一次 43ms（含后端构造与 PNG 编解码）、900×600 一次 337ms（含 Qt 应用与引擎初始化） | 4K 那一格是读数用例 `WinRTImageOcrEngineFixture.ReportsTheCostOfRecognizingA4kImage`（3840×2160 白底 + 96 磅数字，走系统识别后端，**Release 档**）；小图两格是 ctest 的 per-test 计时 |
| 录屏 1080p30 不掉帧、CPU 占用合理 | **没达成**：1920×1080 选区、30 帧档，十秒实测只存下 113/300 帧（≈11.2fps），最大帧间隔 148ms，这一轮进程占掉 85.7% 一个核 | 真的 `RecordingService` 在真屏幕上跑十秒，数 `frameStored` 与帧间隔；CPU 取 `GetProcessTimes` 的进程时间除以墙钟。两道墙拆开看，第一道已经换掉：抓一帧（2560×1440）原来的中位 34ms 出自 Qt 的 `grabWindow`（GDI 位图往返），换到 DXGI 桌面重复后同一台机器同一次运行实测 **6.0ms**（Qt 那一份同轮 30.5ms，各 12 次中位，量法就是 `QScreenCaptureSourceFixture.ReportsMedianGrabCostOfBothPrimitives` 这条读数用例，它不断言时间）；剩下的墙是 PNG 落盘中位 53ms/帧（约 210KB）还留在界面线程上（见[路线图](Roadmap.md#路线图后续计划)），所以 30fps 仍差着——要达标还得把落盘那一段也交出去或换成 `rawvideo` 管道。顺一条反直觉的实测：Qt 的 PNG 压缩档不是省时间的开关，`quality=1` 要 168ms，比默认档慢三倍 |
| 录屏成品的时长与录的那一段一致 | 6.00 秒那一轮编出来 ffmpeg 自报 6.12 秒；旧写法同一轮是 2.33 秒的快放 | 命令里的 `-framerate`（以及 GIF 滤镜里的 `fps=`）按「这一轮的帧数 × 1000 / 毫秒」写成有理数，不再用配置里那档目标帧率——短了的帧序列按目标帧率铺就是快放，音轨还会被 `-shortest` 截尾。端到端用例读 ffmpeg 自己报的 `Duration` 来断：三帧摊在两秒上，成品就该写着 2.00 秒 |
| 编码前的编码器探测耗时 | 本机 1920×1080 单档实测：libx264 60ms（缺件立刻失败）、NVENC 187ms、QSV 1583ms、AMF 574ms、mpeg4 77ms；本机选中 NVENC 走的是前两档共 247ms，五档全试完是 2481ms | 三帧到 `null` 输出的探测命令，参数按真录屏尺寸、帧率与画面码率给；选中即停，只有 MP4 走这一步，GIF 不需要 |
| 贴图拖动流畅、鼠标穿透不抢焦点 | 定性验证：拖动走 `PinTransform` 的增量换算（有用例钉数值），穿透由平台侧 `setMouseThrough` 落地 | 主观流畅度无法用断言钉；这里只承诺「没有动画在拖动的路上插队」 |

（Debug 档只留作「两档不可混用」的对照）：

| 读数 | Release 实测 | 方法与 Debug 对照 |
| --- | --- | --- |
| 冷启动（进程起 → 自检报出就绪） | 中位 **391ms**（7 轮，min 388 / max 409） | `python scripts/measure-cold-start.py --exe build/release/bin/GyanisScribe.exe`——`--selftest` 走与用户双击同一条启动路（建控制器、装托盘、开窗口、登记热键）并自己退出；Debug 档同一脚本读到 939ms |

## 参与贡献


改动要么修掉错误行为，要么加上需求里的能力。上手顺序：

1. 按[从源码构建](#从源码构建)跑一次本机的构建脚本——它一条命令包含配置、编译与 `ctest`，绿了才谈改动。
2. 写完先跑 clang-format（仓库根的 `.clang-format`，`ColumnLimit: 180`），只递给源文件，别把 `CMakeLists.txt` 喂进去。
3. 再跑本机门禁：`scripts\WindowsBuild.bat <preset>`。改到并发、生命周期或跨线程代码时，
   目前没有 TSan 档可跑（随容器设施移除，恢复条件见上文路线图）——**本机全绿不构成并发正确性的证据**。
4. 加功能要带用例，`tests/` 的目录结构逐级镜像 `src/`；每条用例说明它钉住什么，并且能红：
   把实现改回缺陷行为确认这一条会失败，再提交。
5. 提交信息用中文写「为什么」而不是「做了什么」，一次提交只讲一件事，
   格式是约定式提交 `<类型>[(范围)]: <描述>`（类型取 `feat` / `fix` / `refactor` / `perf` / `test` / `docs` / `build` / `chore`）。

规范要点（需求原文已迁至仓外 `GyanisScribe-Reports/`；可跑判据见 `tests/Style/` 三条门禁）：

- 文件与类名 PascalCase、接口 `I` 前缀、函数 camelCase、成员 `m_` 前缀、常量 `k` 前缀，标识符不用缩写。
- 声明处中文 Doxygen（重写的方法要独立写全），实现体在分支、状态流转、加锁、魔法数字处写中文 `//`；
  注释只留「为什么」，不写实现历史与「旧实现怎样、现在怎样」。
- 可恢复错误返回 `std::expected<T, Error>`，错误文案中文且可操作（写清「原因 + 替代做法」）；
  不许静默失败、取整、回绕、把「不支持」悄悄当成「按默认处理」。
- 一切要显示给用户的文本走 `Base::uiText()`，并且同步进翻译目录（`Style.TranslationCatalog` 会拦漏项）。
- 图标必须是原创 SVG：`viewBox="0 0 24 24"`、`currentColor`、描边 2、圆角端点，
  只经 `IconProvider` 加载；不下载、不引用、不复制任何现成图标库或任何现有产品的素材。
- 零告警是硬判据：MSVC 侧每个目标都带 `/W4 /WX`；编译器不报的漏项
  由 `Style.SourceConventions` 与用例兜住。
